## What did you read first, and did it help?
I read the README.md first to get a sense of what the author had already implemented as well as what they didn't get around to yet. It helped me understand what I needed to implement but the document was a bit hard to follow because it was really long and used some technical jargon I didn't understand. I had to use AI to help me transcribe it into more plain language. I was also having trouble understanding the priorities because it wasn't that obvious and I had to go into the phase2_goals document to find that information.
## Was the spec clear? Could you tell what the author wanted? Were the acceptance criteria checkable or vague?
The SPEC was pretty clear for the most part and I could tell what the author wanted. However, it was 598 lines, on top of the readme being 166 lines and the phase2_goals being 176, so it was pretty overwhelming to read. The author says in the spec that the detailed rules were AI-assisted which might be why it reads like it would be suited to feed to an AI tool. To be fair, the spec does open with a general overview to give the person a good sense of the game but I had to nonetheless ask the AI to read the documents because it wasn't realistic for me to read through all of it, considering a lot of it was also very specific numbers and edge cases. The acceptance criteria was checkable and included clear action items. 
## What made the code easy to work with? Be specific: "good comments" tells the author nothing, "the collision logic was one function with a docstring stating its assumptions" tells them everything.
I think the goals were very specific and most of the gameplay tests gave me clear instructions on what is considered "Met" versus "Partially met" or "unmet" which was very helpful. The code was also pretty easy to build on top of in the fact that it was pretty easy for my AI tool to make changes without having to alter much of the code. for example, adding a whole new specieis only took one line in the species table, plusi ts drawing code. Also my AI tool noted that the spawn changes only required 7 of the author's lines to be edited and all of the bird-placement logic lived in one function in one file (spawn.js)
## What cost you time? Again specifically (e.g. cryptic names, a 400-line single file, an unstated environment assumption, a documented feature that wasn't there).
Actually having to test all of the Gameplays took a lot of time because I had to physically interact with the game and determine for myself whether or not, say the jumps were "fair" in that it wasn't sometimes impossible or that changing the FPS still resulted in the same metres flown on a run where I pressed nothing and simply fell (no transfers made). There was also that short-window bug I found where if you made the browser shorter, it wouldn't compress the left side so the actual game screen was cut off. 
## What one thing would you ask the author to do differently next time?
One thing I would ask the author to do differently next time is include some more specific instructions in the game itself on how to play because it was a lot more efficient for me to just play the game and sort of figure out how it works alongside reading the SPEC briefly but I had to do a lot of trail and error to figure it out since I had never played a version of this type of game before. A specific instance of this is like I wasn't sure what the ring under the person meant.
